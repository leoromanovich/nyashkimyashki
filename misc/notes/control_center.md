Ты работаешь в репозитории базы знаний в Obsidian-like markdown-формате. Нужно интерактивно интегрировать в эту базу минимальный process-agnostic подход **Control Center** для нескольких связанных репозиториев.

Цель: не построить тяжелую систему автоматизации, а превратить существующую базу знаний в удобную точку входа для человека и coding agents. После интеграции агент должен быстро понимать, какие репозитории существуют, за что они отвечают, как они связаны, где лежит важная документация, как начинать cross-repo задачу и как не потерять знания после работы.

## Важный контекст

В базе уже есть skill `grill-me-with-docs`, адаптированный под работу с этой базой знаний. Используй его как основной инструмент discovery/refinement:

* чтобы найти существующие связанные заметки;
* чтобы выявить противоречия и пробелы;
* чтобы задавать мне точечные вопросы по уже найденным документам;
* чтобы не выдумывать структуру с нуля, если она уже частично описана;
* чтобы превратить разрозненные заметки в минимальный операционный слой Control Center.

Не превращай работу в большой рефакторинг всей базы. Действуй малыми итерациями.

## Режим работы

Работай интерактивно.

Сначала ничего не переписывай массово. Начни с анализа текущей структуры и существующих заметок. Затем предложи минимальный план изменений. После моего подтверждения вноси изменения маленькими порциями.

На каждом шаге показывай:

1. что ты нашел;
2. какой вывод из этого делаешь;
3. какие файлы предлагаешь создать или изменить;
4. какие вопросы нужно уточнить у меня;
5. что можно отложить.

Не задавай слишком много вопросов сразу. Лучше 3–7 хорошо сфокусированных вопросов за итерацию.

## Что НЕ нужно делать

На первом этапе не нужно:

* добавлять submodules;
* проектировать remote runners;
* описывать SSH/GPU/LLM-heavy сценарии;
* строить CI/CD;
* делать dashboards;
* делать graph database;
* делать embeddings/RAG;
* переписывать всю базу под новую структуру;
* тащить все знания в один огромный `AGENTS.md`;
* менять сами sibling repositories;
* создавать сложную permission-систему.

Сейчас нужна минимальная Control Center-структура поверх уже существующей базы знаний.

## Целевая минимальная структура

Интегрируй или предложи интегрировать следующие элементы. Если в базе уже есть аналоги, не дублируй их, а аккуратно свяжи.

```text
AGENTS.md
README.md
repos.yaml

docs/
  00-start-here.md
  system-map.md
  glossary.md
  workflows/
    impact-map.md
    cross-repo-change.md
    update-knowledge-base.md
  repositories/
    <repo-name>.md

work/
  TEMPLATE.md
```

Если текущая структура базы отличается, адаптируй пути под нее. Не ломай существующую Obsidian-like навигацию.

## Основные артефакты

### 1. `repos.yaml`

Создай или предложи создать manifest репозиториев.

Минимальные поля:

```yaml
version: 1

repos:
  - name: example-repo
    local_path: ../repos/example-repo
    remote: git@github.com:org/example-repo.git
    default_branch: main
    role: Short description of responsibility
    language: python
    docs:
      - docs/repositories/example-repo.md
    common_commands:
      status: git status
      test: pytest
    depends_on: []
    used_by: []
    notes:
      - Important caveat
```

Не требуй сразу заполнить идеально. Лучше собрать черновик с пометками `TODO`.

### 2. `AGENTS.md`

`AGENTS.md` должен быть коротким входным файлом, а не энциклопедией.

Он должен объяснять:

* что этот repository является Control Center;
* где смотреть карту репозиториев;
* где смотреть system map;
* как начинать cross-repo задачу;
* что перед правками нужно делать impact map;
* что нельзя редактировать sibling repositories без явного разрешения;
* что новые знания нужно возвращать в базу.

### 3. `docs/00-start-here.md`

Это человеко- и агенточитаемый стартовый файл.

Он должен содержать:

* краткое назначение базы;
* список основных репозиториев;
* ссылки на system map, workflows, repository cards;
* типовые cross-repo изменения;
* где лежит source of truth.

Сохраняй Obsidian-style ссылки `[[...]]`, если они используются в базе. Где полезно, добавляй рядом обычный markdown-путь.

### 4. `docs/system-map.md`

Сделай или обнови обзор системы.

Минимально:

* какие репозитории входят в систему;
* какие основные потоки зависимостей;
* какие репозитории производят контракты;
* какие потребляют;
* где документация, SDK, examples, infra, runtime;
* какие изменения обычно затрагивают несколько репозиториев.

Не пытайся сделать исчерпывающую архитектурную документацию. Нужна практичная карта для начала работы.

### 5. `docs/repositories/<repo>.md`

На каждый важный репозиторий нужна короткая карточка.

Шаблон:

````markdown
# <repo-name>

## Role

...

## Local path

`...`

## Remote

`...`

## Main commands

```bash
...
````

## Important directories

* `...` — ...

## Contracts produced

* ...

## Contracts consumed

* ...

## Common cross-repo effects

When ... changes:

* update ...
* check ...

## Known traps

* ...

````

Используй существующие заметки из базы, не выдумывай. Если информации нет, ставь `TODO`.

### 6. `docs/workflows/impact-map.md`

Это ключевой workflow.

Он должен требовать, чтобы перед нетривиальной задачей агент составлял impact map:

```markdown
## Goal

...

## Likely affected repositories

| Repository | Why affected | Change type |
|---|---|---|

## Contracts affected

- ...

## Compatibility risk

- backward compatible / breaking / unclear

## Files/directories to inspect first

- ...

## Checks to run

- ...

## Proposed merge order

1. ...

## Open questions

- ...
````

### 7. `docs/workflows/cross-repo-change.md`

Опиши минимальный процесс cross-repo задачи:

1. понять цель;
2. прочитать `AGENTS.md`, `repos.yaml`, `system-map.md`, relevant repository cards;
3. сделать impact map;
4. создать task file в `work/`;
5. создать worktree workspace, если нужны правки;
6. менять только явно затронутые репозитории;
7. запустить релевантные проверки;
8. выдать отчет: changed repos, tests, risks, merge order, knowledge updates.

### 8. `docs/workflows/update-knowledge-base.md`

Опиши правило возврата знаний:

После задачи агент должен предложить, какие знания добавить в Control Center:

* новые зависимости между репозиториями;
* новые known traps;
* новые команды сборки/тестов;
* новые контракты;
* новые типовые workflows;
* устаревшие заметки;
* противоречия между документацией и кодом.

### 9. `work/TEMPLATE.md`

Создай шаблон рабочей задачи:

```markdown

...

- [ ] ...
```

## Как использовать `grill-me-with-docs`

В discovery-фазе:

1. Найди существующие документы про репозитории, архитектуру, зависимости, процессы, команды, сборку, деплой, SDK, API, examples, infra.
2. С помощью `grill-me-with-docs` проверь, какие документы уже отвечают на вопросы Control Center.
3. Составь список найденных источников и коротко объясни, какие из них станут основой для новых файлов.
4. Найди пробелы и противоречия.
5. Задай мне точечные вопросы только по тем пробелам, которые блокируют минимальную структуру.

Не используй `grill-me-with-docs` как повод задавать мне десятки вопросов. Его задача — сначала выжать максимум из уже существующей базы.

## Первый этап работы

Начни с read-only анализа.

Сделай следующее:

1. Осмотри структуру базы знаний.
2. Найди существующие документы, связанные с репозиториями, архитектурой, workflow, сборкой, интеграциями и зависимостями.
3. Примени `grill-me-with-docs`, чтобы получить grounded summary по текущим знаниям.
4. Составь краткий отчет:

```markdown
## What already exists

...

## Likely repository map

...

## Existing docs that can become Control Center docs

...

## Missing minimal pieces

...

## Proposed minimal file changes

...

## Questions for user

1. ...
2. ...
3. ...
```

После этого остановись и жди моего подтверждения перед созданием или массовым изменением файлов.

## Принцип адаптации

Если уже есть хорошая заметка, не создавай дубликат. Лучше:

* добавить ссылку из `00-start-here.md`;
* добавить карточку-обертку;
* переиспользовать существующий файл как source of truth;
* добавить секцию `Control Center notes`;
* поставить TODO на будущую нормализацию.

## Definition of Done для первой итерации

Первая итерация считается завершенной, когда есть:

* `AGENTS.md`;
* `repos.yaml`;
* стартовая страница или ее эквивалент;
* system map или ее черновик;
* impact map workflow;
* cross-repo change workflow;
* task template;
* минимум одна repository card;
* список TODO для недостающих repository cards;
* никакие sibling repositories не изменены.

Работай прагматично. Control Center должен помогать начинать задачи и удерживать контекст, а не становиться еще одной тяжелой системой, которую нужно обслуживать.
